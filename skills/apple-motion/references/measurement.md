# 측정 — Apple 동작을 눈대중이 아니라 숫자로

## 왜 필요한가

이 스킬의 첫 카탈로그는 "시스템 HUD"를 기억과 추측으로 만들었고, 사용자가 시뮬레이터에서 돌려 보고 **"애플스럽지 못하다"**고 평가했다.
녹화해서 보니 이유가 있었다: 점선처럼 읽히는 16개의 점, 흰 바탕에 거의 안 보이는 연한 회색 알약, 들어올 때와 나갈 때 모두 0.3초씩
안개처럼 번지는 블러 디졸브 — 어느 Apple 기기의 HUD도 아닌 **이 앱 노치 HUD의 변형**이었다. 컴파일이 통과해도 보이는 모양은 보장되지 않는다.

그래서 Apple 동작을 요청받으면 **기억으로 만들지 않고, 레퍼런스를 측정해서 만든다.** 그리고 내 구현도 같은 방법으로 녹화해 비교한다.

## 워크플로

1. **레퍼런스를 받는다.** 사용자에게 실제 Apple 기기(또는 앱)에서의 화면 녹화를 요청한다. 아래 "무엇을 녹화하나" 참고.
2. **눈으로 본다.** `scripts/filmstrip.sh`로 프레임을 시간 라벨과 함께 한 장으로 펼친다 — 어떤 속성이(위치·크기·투명도·블러) 어떤 순서로 움직이는지부터 적는다.
3. **숫자로 잰다.** `scripts/track_video.sh`가 영역의 변화를 프레임마다 CSV로 뽑고, `scripts/fit_spring.py`가 스프링을 맞춰 **범위와 함께** 보고한다.
4. **구현한다.** 측정값에 가장 가까운 `Motion` 어휘/Apple 프리셋을 고른다. 범위에 여러 프리셋이 걸리면 구분되지 않는다고 말하고 10%→90% 시간과 오버슈트를 기준으로 삼는다.
5. **같은 방법으로 재측정한다.** 시뮬레이터에서 내 구현을 녹화해 같은 도구로 재고 레퍼런스와 겹쳐 본다. 어긋나면 4번으로.

## 도구

```bash
# ① 프레임을 필름스트립으로 (구간, 개수, 한 줄에 놓을 개수, [잘라낼 영역 x y w h])
scripts/filmstrip.sh ref.mov strip.png 2.0 3.2 16 4 0 330 1206 330

# ② 영역의 변화를 CSV로 (영역 x y w h, 배경 프레임 시각, 분석 구간, 임계값, [고정 배경색])
scripts/track_video.sh ref.mov 150 340 900 210 2.75 1.5 7.5 8 > data.csv         # 요소가 없던 프레임을 배경으로
scripts/track_video.sh ref.mov 0 400 1206 240 0 0.3 9.8 60 253 > data.csv         # 요소가 항상 있으면 고정 배경색(253)

# ③ 한 번의 전환에 스프링 맞추기
python3 scripts/fit_spring.py data.csv --col bw --from 3.35 --to 4.4
python3 scripts/fit_spring.py --selftest                                          # 도구 자체 검증 (≈25초)
```

**어떤 열을 잴까** — 신호가 깨끗할수록 결과가 믿을 만하다.
| 열 | 무엇 | 잘 맞는 경우 | 조심 |
| --- | --- | --- | --- |
| `bw` `bh` `bx` `by` | 달라진 픽셀의 바운딩 박스 | **선명한 가장자리**의 크기·이동 (Dynamic Island 폭, 시트 높이) | 블러·그림자가 있으면 가장자리가 번진다 |
| `mean` | 평균 밝기 차이 ≈ 투명도 × 면적 | 투명도 페이드 | 블러·크기·내용 변화가 섞이고, 입력이 반복되면 끝값이 흔들린다 |
| `count` | 달라진 픽셀 수 | 면적 변화 | 내용이 바뀌면 같이 변한다 |

## 정확도 — 검증한 만큼만 말한다

- **시간축은 정확하다.** 시뮬레이터 녹화에서 `linear(0.5s)`를 재면 10%→90%가 정확히 0.400s, 10%→50%가 0.200s로 나왔다(오차 없음).
- **10%→90% 시간**은 정답을 아는 5개 스프링(smooth 0.30/0.60, snappy 0.42 ×2, bounce 0.35/0.28)에서 정답의 **0.90~0.99배**(평균 약 5% 짧게)였다. 시간 비교는 이 값을 우선 믿는다.
- **파라미터(response, 감쇠비)** 는 서로 보완해서 한 값으로 못 박기 어렵다. 노이즈가 0이면 정확히 복원되지만(오차 0.1%), 실제로는 두 값이 섞인다.
  그래서 도구는 **범위**를 낸다. 범위는 합성 데이터(σ=0.02, 60fps, 36케이스)에서 정답 포함 97%, 정답을 아는 실제 녹화 9창(알려진 스프링 5 + Dynamic Island 폭 4)에서 9/9로 보정했다 — **표본이 적으므로 "대략 95%"로 읽는다.**
  평균 폭은 response 약 0.17s, 감쇠비 약 0.36이다. 즉 한 번의 60fps 녹화로는 **smooth/snappy/bouncy를 항상 구분하지는 못한다.**
- 구분력을 높이려면: 노이즈가 적은 신호(`bw`, 선명한 가장자리), 120fps 이상, 전환 하나만 담은 짧은 구간. (합성 기준 노이즈 0.005·120fps에서 response 폭 0.05s, 감쇠비 폭 0.15로 줄었다.)
- **스프링이 아닌 것**은 맞지 않는다. `rmse`가 0.08을 넘으면 ease/linear일 수 있다 — 이때는 파라미터가 아니라 10%→90% 시간과 곡선 모양을 그대로 쓴다.

## 시뮬레이터에서 내 구현을 녹화하기

`mcp__Claude_Code_iOS_Simulator`는 `xcode-select`가 Xcode를 가리켜야(sudo 필요) 돌아간다. 그게 안 돼 있어도 `DEVELOPER_DIR`로 `simctl`을 쓰면 된다.

```bash
export DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer
xcrun simctl list devices booted                                   # UDID 확인
xcrun simctl launch <UDID> <bundle.id> -autoDemo hud               # 앱이 실행 인자로 데모를 저절로 돌리게 만들어 두면 탭이 필요 없다
xcrun simctl io <UDID> recordVideo --codec h264 --force out.mov &  # 끝낼 땐 kill -INT 로 종료
# 빌드: env -i PATH="$PATH" HOME="$HOME" DEVELOPER_DIR=$DEVELOPER_DIR xcodebuild -project … -scheme … -sdk iphonesimulator -destination 'id=<UDID>' CODE_SIGNING_ALLOWED=NO build
```
- 녹화는 **가변 프레임**이다 — 화면이 안 바뀌는 동안은 프레임이 없고, 움직이는 동안은 120fps까지 나온다. 정상이다.
- 하네스의 전체 환경 변수를 넘기면 `swiftc`/`xcodebuild`의 SwiftUI 매크로 플러그인 서버가 실패할 수 있다. `env -i`로 최소 환경만 넘긴다.
- 자동 재생용 실행 인자(`-autoDemo`)를 앱에 넣어 두면 사람 손 없이 반복 녹화할 수 있다.

## 무엇을 녹화하나 (사용자에게 요청할 때)

- **해당 기능을 실제 Apple 기기에서** 시작부터 끝까지, 앞뒤 1초 여유를 두고. 같은 동작을 3~4번 반복하면 평균을 낼 수 있다.
- **가능하면 60fps 이상.** iPhone/iPad 화면 기록은 60fps 정도, 더 촘촘히 보려면 다른 카메라의 슬로모션(240fps)으로 화면을 찍는다.
- 시스템 HUD(볼륨·밝기)처럼 **시스템이 그리는 UI는 화면 기록에 안 잡힐 수 있다**(기기·OS에 따라 다를 수 있어 확실하지 않다). 안 잡히면 다른 카메라로 촬영한다.
- 가능하면 **라이트 모드와 다크 모드**, 그리고 **동작 줄이기를 켠 상태**도 한 번씩.
- 측정할 것(기능마다 공통): 시작·끝의 위치와 크기 / 등장·퇴장 시간(10%→90%) / 스프링인가 ease인가 / 오버슈트가 있는가 /
  동시에 움직이는 속성들의 순서(어느 것이 먼저, 어느 것이 늦게) / 입력이 반복될 때(키를 누르고 있을 때) 반응 / 최대·최소값에서의 반응.
